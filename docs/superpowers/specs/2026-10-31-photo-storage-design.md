# Private photo storage

Issue: #96 (sub-issue of #66). Requirements: FR-05, NF-01, NF-02, NF-04, TC-03; [ADR 0001](../../adr/0001-technology-baseline.md) "Photo storage".

## Intent

Accepted photos are the photographer's only copy of their originals. The API (uploads, serving)
and the worker (previews) need one private, durable place to read and write them, with a path
scheme that cannot be abused by a user-controlled filename and writes that never leave a
half-written file that looks like a stored photo.

## Goals

- A persistent volume shared by the API and the worker, outside public static directories and
  container writable layers.
- One cohesive storage layer that owns paths and file operations.
- Atomic writes; an interrupted or disk-full write reports failure and leaves nothing visible.
- The layout and its consequences recorded in a short ADR.

## Non-goals

- Upload endpoints, validation, image processing, the `photos` table or serving routes
  (#98, #99, #101).
- Gallery deletion and cleanup of stale files (#73, and the repository cleanup guidance).
- Object storage, a storage trait, or any backend other than the local filesystem (TC-03).
- Browsable files or backup tooling; backup/restore is deferred by the PRD.

## Anti-goals

- Any path component derived from a user-supplied string. Original filenames live only in the
  database (#98) and are used for display and ZIP entry names, never as paths.
- A volume the API or worker cannot write because it was created root-owned.

## Approaches

1. **New crate `pp-storage` (chosen).** A small crate beside `pp-database`, depended on by the
   API and the worker. Cohesive, and the typed key makes unsafe paths unrepresentable. Costs one
   more crate.
2. **A module in `pp-core`.** No new crate, but `pp-core` already mixes config, email and
   notifications; file I/O would make it less cohesive.
3. **A storage trait with a filesystem implementation.** Rejected: TC-03 forbids an extensible
   storage framework for hypothetical backends.

## Decisions

Decided with the product owner:

- Approach 1.
- Files are named by UUID: `<photo-dir>/<workspace-id>/<gallery-id>/<photo-id>-<variant>` (no extension: the format is validated at upload and a derivative's format may change). The volume
  is not browsable and is not a usable backup without the database. Accepted because backup is
  deferred.

My calls (to check while reading):

- **Typed key.** `PhotoKey { workspace, gallery, photo, variant }` is built from UUID newtypes
  only; `variant` is an enum (`Original`, `Thumbnail`, `Preview`). There is no `Final` variant: finished
  photos are an independent set with no mapping to proofs (FR-10), so a finished photo has its own
  photo id and its stored file is that photo's `Original`; #70 decides how the two sets are told apart. The path is derived from it, so traversal is impossible by construction.
- **Directory.** A typed setting `PP_PHOTO_DIR` / `--photo-dir` / `photo_dir` (default for development under a local directory),
  parsed once into a validated type. `PhotoStorage::open` checks that it is an existing,
  writable directory and fails startup otherwise.
- **Atomic write.** A write is staged as a temp file in `<photo-dir>/.tmp` (same filesystem, so
  `rename` is atomic), flushed and synced, then `commit` renames it into place. Dropping a staged
  file without committing removes it. Commit never overwrites silently: a derivative being
  regenerated by a retried job replaces the previous file atomically, an original is written
  once.
- **Errors.** A typed `StorageError` distinguishes disk-full from other I/O failures so callers
  can report an accurate reason.
- **Reads and removal.** `open(&key)` returns a read handle and `remove(&key)` deletes one
  file. Directory and gallery removal belong to #73.
- **Compose.** A named volume `photo-data` mounted at `/var/lib/pp/photos` in `api` and
  `worker`. Both Dockerfiles create that directory owned by the `pp` user so a fresh volume is
  writable. The worker gains `PP_PHOTO_DIR`.

## Left to the builder

- Exact crate API shape and error variants, and the async I/O flavour (`tokio::fs`).
- How to test disk-full without a real full disk (error-kind mapping unit test, or a size
  limited tmpfs where available).
- Whether crash-leftover temp files are purged at startup; an age-based purge is safe for two
  processes, purge-all is not.

## Verification

Tests for path containment, commit visibility (nothing readable before commit, file present
after), drop-without-commit leaving nothing, overwrite of a derivative, disk-full mapping, and
startup failure for a missing or read-only root. `docker compose up` shows both services
writing to the shared volume as `pp`.
